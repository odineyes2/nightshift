# 파일 분할 계획서 — 요청 하나당 읽는 코드량 줄이기

작성: 2026-09-27 · 상태: 1단계 완료(번들 방식), 2단계 대기

## 1. 왜 하나

Claude에게 기능 하나를 고쳐 달라고 하면, 관련 코드가 거대한 파일 한가운데 있어서 넓게 읽게 되고
그 내용이 대화 내내 입력 토큰으로 반복 청구된다.

| 파일 | 지금 | 문제 |
|---|---|---|
| `static/index.html` | 16,290줄 (CSS 3,200 · 마크업 1,330 · JS 11,665) | 화면 전체가 한 파일. "Jobs 카드 한 줄"을 고쳐도 이 파일을 연다 |
| `server/app.py` | 6,434줄 (API 161개) | 인증·파드·작업·모델·갤러리·프로젝트가 한 파일 |

**목표**: 기능 하나를 고칠 때 여는 파일이 1~2개, 파일 하나가 대략 1,500줄 이하.

## 2. 원칙

1. **동작은 하나도 바꾸지 않는다.** 코드를 옮기기만 하고, 이동과 수정을 한 PR에 섞지 않는다.
2. **빌드 과정은 만들지 않는다.** 지금처럼 파일을 그대로 서빙한다(`<script src>`, `<link rel=stylesheet>`). npm 번들러 등은 도입하지 않는다.
3. **기계적으로 자르고, 기계적으로 검증한다.** 사람이(Claude가) 파일을 통째로 읽고 다시 쓰지 않는다 — 기존 구역 표시(`// ---- 이름 ----`, `# ---- 이름 ----`)를 경계로 스크립트가 줄 범위를 잘라 옮긴다.
4. **되돌리기 쉽게.** 단계마다 PR 하나. 문제가 생기면 그 PR만 되돌리면 된다.

## 3. 1단계 — `index.html` 분할 (효과가 가장 큼)

### 결과 구조
```
static/
  index.html          마크업만 (~1,400줄) + 아래 파일을 순서대로 불러오는 태그
  css/                기존 <style>를 구역별로 (base · layout/nav · jobs · pods · gallery · models · board · misc 등 8개 안팎)
  js/                 기존 <script>를 기능별로, 원래 순서 그대로
    core.js           공용 유틸·전역 상태·fetch 래퍼
    pods.js           파드 목록·대시보드 카드·파드 추가/편집·길게 눌러 삭제·RunPod 켜기/끄기
    jobs.js           Job Queue 카드·상세 모달·파드/프로젝트 이동
    newjob.js         새 작업 폼(템플릿 옵션·참조 슬롯·입력 이미지·최근 워크플로우·CSV 편집)
    wizard.js         마법사 1~4단계·적용·워크플로우 검사·LoRA 트리거
    models.js         모델 탭(등록부·설치 현황·직접 추가)
    account.js        로그인·회원 관리·테마·NSFW
    db.js             DB 탭(RunPod 세션·업데이트 내역·생성 정보)
    routing.js        화면 전환·파드/프로젝트 스코프 바
    gallery.js        갤러리·필터·일괄 작업·라이트박스·메타·참조 세트로 보내기
    video.js          영상 갤러리·영상 편집·자동 재생·OpenCut
    projects.js       프로젝트·홈 대시보드
    board.js          프로젝트 보드(무한 캔버스·카드·되돌리기) — 1,700줄이라 필요하면 둘로

```
(정확한 묶음은 구역 표시 75개를 기준으로 자를 때 확정한다.)

### 왜 안전한가 / 조심할 점
- 여러 `<script>` 파일은 전역 변수를 그대로 공유하므로, 원래 순서대로 이어 붙이면 한 파일일 때와 같다.
- **예외 하나**: 한 파일 안에서는 함수 선언이 파일 전체로 끌어올려지지만, 파일을 나누면 앞 파일이 **불러오는 순간 바로** 뒤 파일의 함수를 부르면 오류가 난다(이벤트 처리기 안에서 부르는 건 괜찮음). → 자른 뒤 이런 호출을 스크립트로 찾아내고, 해당 초기화 코드는 `init.js`로 옮긴다.
- **브라우저 캐시**: JS/CSS가 따로 캐시되므로 업데이트 뒤 옛 파일이 섞일 수 있다. → 서버가 `/js/*`, `/css/*`에 `Cache-Control: no-cache`(ETag로 재검증, 바뀐 것만 새로 받음)를 붙인다.

> **실제 적용(1단계)**: 파일별 `<script>`로 나눠 불렀더니 위 "예외"(파일 사이 끌어올림) 때문에 오류가 났다.
> 그래서 서버가 `static/js/*.js`를 번호 순으로 이어 붙여 `/js/bundle.js` 하나로 보낸다(CSS도 `/css/bundle.css`).
> 브라우저가 실행하는 코드는 분할 전과 글자까지 같고, 저장소에서는 파일이 나뉘어 있다.

### 검증
1. **바이트 비교**: 새 JS 파일들을 로드 순서대로 이어 붙인 결과 = 원래 `<script>` 내용(CSS도 동일). 옮기다 한 글자라도 빠지면 여기서 걸린다.
2. `node --check`로 파일마다 문법 검사.
3. 헤드리스 브라우저: 모든 탭(Home·Pods·Jobs·Gallery·Videos·Models·Danbooru·DB·Admin)과 주요 모달을 열어 **페이지 오류 0건**, 기존 기능 테스트(작업 카드·RunPod 버튼·LoRA 트리거 등) 재실행.

## 4. 2단계 — `app.py` 분할

### 결과 구조
```
server/
  app.py              앱 생성·미들웨어·라우터 등록·시작 처리만 (~300줄)
  core/
    state.py          작업 목록(jobs)·잠금·저장/복원
    runtime.py        파드별 워커·dispatch·대기 큐 스케줄러·모델 받기 감시
    comfy.py          ComfyUI object_info·워크플로우 검사·모델 누락 계산
  routes/             FastAPI APIRouter — 기능별
    auth.py  admin.py  pods.py  jobs.py  models.py  outputs.py
    projects.py (보드 포함)  db_logs.py  video.py  share.py  misc.py
```
- 의존 방향은 한쪽으로만: `routes/* → core/*`, `core`는 `routes`를 모른다(순환 import 방지).
- 1단계보다 결합이 강해서(전역 `jobs`·`lock`·`pod_runtimes`를 여러 곳이 공유) **2~3개 PR로 나눈다**: (a) core 추출 → (b) 라우터 절반 → (c) 나머지.

### 검증
1. **API 목록 비교**: 분할 전후 `app.routes`의 (메서드, 경로) 집합이 똑같은지.
2. `py_compile` + 서버 기동 + 오늘 쓴 가짜 파드 E2E(작업 생성 → 시작 → 모델 받기 → 배정, RunPod 켜기/끄기, 로그인·MCP 키 인증).
3. `mcp_smoke_test.py --skip-generation`.

## 5. 원격 제어 세션과의 충돌 — 꼭 지킬 순서

분할은 `index.html`/`app.py`를 통째로 재배치하므로, **그 사이 다른 세션이 이 파일을 고치면 병합이 사실상 불가능**하다.

1. 분할 PR을 만드는 동안 원격 제어 세션은 `index.html`/`app.py`를 고치지 않는다(작업을 멈추거나 다른 파일만).
2. 원격 제어 세션에 커밋 안 된 변경이 있으면 먼저 커밋·push한다 → 분할은 그 최신 main 위에서 한다.
3. 분할 PR 병합 → 홈서버 `git pull` → 원격 제어 세션에 "파일 구조가 바뀌었다, CLAUDE.md의 파일 지도를 보라"고 알린다.

## 6. 마무리

- `CLAUDE.md`의 "index.html 길찾기"를 **파일 지도**(어떤 기능이 어느 파일에 있나)로 바꾼다. 이게 토큰 절약의 핵심 — Claude가 파일을 뒤지지 않고 바로 해당 파일로 간다.
- README의 디렉터리 구조 절 갱신.

## 8. 진행 순서 요약

1. 이 계획서 검토 · 원격 제어 세션 상태 확인
2. 1단계 PR (index.html) → 검증 → 병합 → 홈서버 반영(재시작 필요: 캐시 헤더 때문에 app.py 한 줄 변경 포함)
3. 2단계 PR 2~3개 (app.py) → 각각 검증 → 병합 → 재시작
4. CLAUDE.md·README 갱신 (각 단계 PR에 포함)
