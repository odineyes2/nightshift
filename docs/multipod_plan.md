# 다중 파드 전환 계획 (nightshift → 워커 플릿 관리자)

nightshift를 "ComfyUI 한 대에 작업을 밀어넣는 잡 큐"에서 **"여러 대의 워커(파드)를 거느리고
관리하는 대시보드"**로 바꾸는 작업의 계획서다. 착수 전에 무엇을 왜 하는지, 어떤 순서로 하는지,
무엇은 하지 않는지를 못 박아 두기 위한 문서다.

---

## 1. 왜 지금인가

이미 절반은 와 있다. 직전까지의 A-1~A-5 작업이 전부 "nightshift와 워커는 같은 머신이 아니다"를
전제로 깐 것이었다.

| 작업 | 내용 | 다중 파드에 주는 것 |
|---|---|---|
| A-1 | ComfyUI 접속 주소를 런타임 설정으로 | 주소가 데이터라는 전제 |
| A-2 | 원격 전제의 포트/타임아웃/상태 폴링 정리 | 원격 워커의 상태를 싸게 보는 법 |
| A-3 | 워커가 꺼져 있으면 작업을 붙잡아 둠 | 파드가 죽어도 큐가 안 무너짐 |
| A-4 | 결과물을 HTTP로 회수 (`comfy_outputs.py`) | 산출물이 워커 디스크에 있어도 됨 |
| A-5 | 같은 입력 이미지를 실행당 1회만 업로드 | 업로드 캐시 키에 이미 워커 주소가 들어 있음 |

즉 다중 파드는 새 방향이 아니라 **이미 가던 방향의 다음 칸**이다. 그리고 지금 큐는 한 번에
하나씩만 돌기 때문에, pod를 두 대 켜도 처리량이 늘지 않는다. GPU 시간을 사서 쓰는 구조에서
이건 실제 손해다.

## 2. 더 큰 그림: 이질적 워커

이 전환의 최종 목적지는 "ComfyUI 여러 대"가 아니다. **서로 다른 종류의 AI 워커들이 각자 다른
일을 하고, nightshift가 그것들을 한 화면에서 관리하는 것**이다 — 어떤 파드는 이미지를 만들고,
어떤 파드는 글을 쓰고, 어떤 파드는 지도를 그린다.

이게 가능한 이유는 nightshift의 실행 구조가 이미 ComfyUI를 거의 모르기 때문이다.

| 이미 일반적인 것 | ComfyUI에 묶인 것 |
|---|---|
| 작업 = (스크립트 + 입력 파일 + 옵션) | `resolve_comfy_url()` — 주소가 하나뿐 |
| 워커가 서브프로세스로 스크립트 실행 | `/object_info` — 능력 조회 |
| 스크립트가 HTTP로 진행률 보고 | `/prompt` + `/history` — 제출·폴링 |
| 결과물이 `job_id/` 폴더에 쌓임 | `/view` — 결과 회수 |
| 큐·재시도·중단·로그·소프트 삭제 | 갤러리가 이미지 전용 |

오른쪽 항목들은 전부 "이 워커에 대해 어떻게 하는가"이고, **드라이버**로 뽑아낼 수 있다.

## 3. 현재 구조의 제약 (구체적 지점)

`app.py`에서 "하나뿐"이라 다중 파드를 막는 전역 상태들:

```
337  comfy_endpoint          접속 주소 설정 1벌
405  job_queue               큐 1개
415  auto_run                자동 실행 플래그 1개
419  current_job_id          실행 중 작업 1개
420  current_process         실행 중 서브프로세스 1개
506  _object_info_cache      모델/노드 목록 캐시 1벌 (url 키가 하나)
959  _comfy_status_cache     연결 상태 캐시 1벌
     worker_loop()           워커 스레드 1개
     stop_current_job()      "그" 실행 중 작업을 중단
     MAX_ACTIVE_JOBS         전역 상한
```

`resolve_comfy_url()`을 부르는 지점은 12곳이다(상태 조회, 모델 목록, 워크플로우 검증, Prompt
Enhance, 워커 실행, 출력 동기화 등). 이 함수들이 전부 **"어느 파드?"를 인자로 받아야** 한다.

### 3.1 다행히 이미 맞아떨어지는 것

- **출력 동기화 키 충돌 없음** — `comfy_output_sync.json`의 키는 `job_id/파일명`이고 `job_id`는
  nightshift가 발급하므로 파드가 달라도 고유하다. `pull_job_outputs()`가 이미 `comfy_url`을
  인자로 받고 있어서, 그 작업을 돌린 파드 주소만 넘기면 그대로 동작한다.
- **입력 이미지 업로드 캐시가 이미 파드별** — A-5의 캐시 키가
  `(comfy_url, 절대경로, 크기, 수정시각)`이라 파드가 다르면 각각 올라간다.
- **GPU 대기(A-3)가 파드 죽음 처리의 기반** — 파드 하나가 죽어도 그 작업을 실패시키지 않는
  로직이 이미 있다.

## 4. 목표 구조

### 4.1 파드 = 주소 + 드라이버

파드는 "ComfyUI 한 대"가 아니라 **드라이버가 붙은 엔드포인트**다.

```python
class PodDriver:
    kind = "comfyui"                        # "shell", "llm-writer", ...

    def resolve(pod)          -> (url, source)  # 이 파드가 가리키는 주소와 그 출처
    def health(pod, timeout)  -> {"ok", "url", "source", "detail"}
    def capabilities(pod, force) -> (url, 능력)  # 모델/노드/도구 목록 (파드별 캐시)
    def job_env(pod, url)     -> dict           # 작업에 실어 보낼 환경변수
    def collect(pod, url, job_id) -> dict|None  # 산출물 회수 요약
    def card(pod)             -> dict           # 대시보드 카드에 실을 요약
```

`card()`를 드라이버에 두는 것이 핵심이다. ComfyUI 카드는 VRAM·생성 장수·썸네일을 보여주고,
글 쓰는 워커 카드는 토큰 수·문단 미리보기를 보여준다 — **카드 렌더링이 워커 종류마다 달라야
이질적 파드 관리가 실제로 성립한다.**

`comfyui` 드라이버는 새로 짜는 게 아니라 기존 코드를 옮겨 담는 것이다:

| 드라이버 함수 | 지금 코드 |
|---|---|
| `health` | `check_comfy_url()` |
| `capabilities` | `fetch_object_info()` |
| `job_env` | `worker_loop()`이 만들던 `COMFY_URL` 환경변수 |
| `collect` | `comfy_outputs.sync_outputs()` |
| `card` | (신규) `/system_stats` + 작업 통계 |

### 4.2 파드 레지스트리

`pods.json` (git 무시 — 배포마다 다름):

```jsonc
{
  "pods": [
    {
      "id": "p_abc123",
      "name": "a100-1",           // 별칭, 화면에 뜨는 이름
      "kind": "comfyui",          // 드라이버
      "url": "http://100.x.x.x:8188",
      "enabled": true,
      "tags": ["gpu", "sdxl"],
      "max_concurrent": 1,        // 이 파드가 동시에 돌릴 작업 수
      "pull_outputs": true,       // 결과물을 HTTP로 끌어올지
      "note": ""
    }
  ]
}
```

런타임 상태(저장 안 함): `status`, `current_job`, `queue_len`, `last_seen`, `latency`,
`capabilities_at`.

`comfy_endpoint.json`은 이 레지스트리로 흡수한다 — 기존 설정이 있으면 파드 1개짜리
레지스트리로 자동 이관한다.

### 4.3 파드별 독립 큐

파드마다 `Queue` + 워커 스레드 + `auto_run` + `current_job`을 갖는다. 3장의 전역 상태들이
전부 파드 밑으로 내려간다. 작업에는 `pod_id`가 붙고, "새 작업 추가"에 파드 선택이 생긴다.

**독립 큐의 대가**: 파드가 죽으면 그 큐가 멈춘다(A-3 덕에 실패하진 않고 `GPU 대기`로 잡혀
있지만, 옆 파드가 놀아도 안 옮겨간다). → 작업 행에 **"다른 파드로 옮기기"** 액션을 넣어
수동으로 해소한다. 자동 배분은 나중에 정책 하나 추가하는 것으로 열어둔다.

### 4.4 대시보드 = 카드 캔버스

```
/            대시보드 (홈)
/pod/{id}    그 파드 스코프의 작업/갤러리/모델
```

카드 그리드는 **카드 타입**을 갖는다. 지금은 `pod` 하나만 구현하되, 그리드가 타입별 렌더러를
부르는 구조로 만들어 두면 나중에 통계 카드·최근 산출물 카드·메모 카드 같은 걸 얼마든지
얹을 수 있다. 카드 크기/배치(1×1, 2×1 등)도 카드가 정한다.

기존 탭(Danbooru / 워크플로우 / 모델 / 갤러리)은 없애지 않고 전역 메뉴로 남는다.

## 5. 단계별 작업

### P0 — 파드 레지스트리 + 드라이버 seam

**목표: 화면은 전혀 안 바뀌고, 파드 1개일 때 지금과 100% 동일하게 동작한다.**

- [x] `pod_registry.py` — `pods.json` 로드/저장, CRUD, id 발급
- [x] `drivers/` — `PodDriver` 베이스 + `comfyui` 드라이버(기존 코드 이식)
- [x] `comfy_endpoint.json` → `pods.json` 자동 이관 (기존 설정 보존)
- [x] `GET/POST/PUT/DELETE /api/pods`, `POST /api/pods/{id}/test`
- [x] `resolve_comfy_url()` 호출 12곳을 "기본 파드"를 거치도록 정리
- [x] `.gitignore`에 `pods.json`
- [x] 검증: 기존 기능 전부 회귀 테스트 (작업 등록→실행→갤러리→출력 동기화)

**드라이버 인터페이스 조정**: 계획서 초안의 `run(pod, job, log)`은 P0에서 만들지 않았다.
작업을 실제로 실행하는 부분(서브프로세스 띄우고 로그 받고 중단 요청 처리)은 워커 종류와
무관한 "일반 실행기"라 드라이버로 내릴 이유가 없었고, 대신 드라이버는 `job_env(pod, url)`로
"이 파드에 작업을 보낼 때 필요한 환경변수"만 기여한다(ComfyUI는 `COMFY_URL`). 완전히 다른
방식으로 작업을 실행하는 워커를 위한 `run()` 훅은 worker_loop을 파드별로 다시 쓰는 P1에서
연다 — 그때가 그 코드를 어차피 손대는 시점이라 위험이 가장 낮다.

### P1 — 파드별 큐/워커/상태

- [x] 전역 상태(`job_queue`/`auto_run`/`current_job_id`/`current_process`/캐시 2종)를 파드별로
- [x] 파드당 워커 스레드, `max_concurrent` 반영
- [x] 작업에 `pod_id` 필드, "새 작업 추가"에 파드 선택
- [x] `POST /api/jobs/{id}/move` — 다른 파드로 옮기기
- [x] `GET /api/pods/summary` — 대시보드가 폴링할 요약
- [x] 파드별 `/object_info` 캐시 → 워크플로우 검증/모델 목록이 파드를 따라감 (P0에서 이미 완료)
- [x] 검증: 파드 2개(가짜 ComfyUI 2대)로 동시 실행, 한쪽 죽였을 때 다른 쪽 영향 없음

**설계 메모 — 옮긴 작업이 두 번 돌지 않게**: 파이썬 `queue.Queue`는 넣은 항목을 도로 뺄 수
없다. 그래서 큐에 이미 들어간 작업을 다른 파드로 옮기면, 옛 파드의 큐에도 그 job_id가 남는다.
워커가 작업을 꺼낼 때 **"이 작업이 아직 내 것인가"를 확인하고 아니면 그냥 버리는** 방식으로
푼다(다시 배차하지 않는다 — 옮긴 쪽이 이미 새 파드 큐에 넣었으므로 여기서 또 넣으면 같은
작업이 두 번 돈다). 기다리는 중(`wait_for_pod`)에 옮겨진 경우도 같은 규칙이다.

**`/api/pods/summary`의 범위**: 값싼 것만 담는다(레코드 + 캐시된 연결 상태 + 큐/실행 상태 +
오늘 만든 이미지 수). 파드별 `/system_stats`(VRAM 등) 같은 추가 왕복은 자체 캐시를 붙여
대시보드 화면을 만드는 P2에서 넣는다.

### P2 — 대시보드 홈

- [x] 대시보드를 첫 화면으로, 파드 스코프 이동
- [x] 카드 캔버스 (타입별 렌더러, 크기 지정 가능)
- [x] `pod` 카드: 상태 점 / 현재 작업 + 진행률 / 대기 수 / 오늘 처리량 / 최근 산출물 / 시작·정지
- [x] 상단 전역 요약 바
- [x] 파드 추가·편집·삭제 UI
- [x] 검증: Playwright로 파드 2개 상태에서 라이트·다크 확인

**라우팅 방식 조정**: 계획서 초안의 `/`·`/pod/{id}` 경로 라우팅 대신 **해시 라우팅**
(`#dashboard`, `#jobs`, `#pod/{id}`)을 썼다. 이 앱은 정적 index.html 한 장이라 경로
라우팅을 쓰려면 서버에 catch-all 라우트를 붙이고 클라이언트에 pushState 처리를 넣어야
하는데, 얻는 것(주소가 예뻐지는 것)에 비해 손대는 곳이 많다. 해시로도 새로고침·뒤로가기·
링크 공유가 다 되고 서버는 한 줄도 안 바뀐다. 나중에 정말 필요해지면 그때 바꾼다.

**파드 스코프의 범위**: "🗂 작업 보기"는 작업 목록을 그 파드 것만 걸러 보여준다. 갤러리·모델
목록까지 파드별로 좁히는 것은 넣지 않았다 — 갤러리는 이미 작업별 보기가 있고, 모델 목록은
파드마다 다를 수 있다는 문제(8번 열린 질문)가 먼저 정리돼야 한다.
→ **P4에서 정리했다.** 모델·워크플로우 화면이 파드 안으로 들어가면서 "어느 파드의 목록인가"가
주소로 결정된다. 갤러리는 그대로 전역이다(산출물은 파드가 아니라 작업에 딸린 것이므로).

### P3 — 이질적 워커 실증

- [x] `shell` 드라이버 — 등록한 머신(로컬 또는 SSH)에서 임의 스크립트 실행
- [x] `shell` 파드용 카드 렌더러 (ComfyUI 카드와 다르게 보인다)
- [x] 산출물이 이미지가 아닐 때 갤러리가 어떻게 되는지 확인

**결과 — 드라이버 seam이 실제로 버틴다.** 셸 파드는 ComfyUI와 공통점이 거의 없는데도
(HTTP 엔드포인트 없음, 모델 목록 없음, 회수할 산출물 없음) 레지스트리·큐·워커·대시보드는
한 줄도 안 고치고 그대로 받았다. 실제로 손댄 곳은 세 군데뿐이고, 셋 다 **원래부터 ComfyUI를
전제하고 있던 자리**였다:

1. **주소 형식 검증** — 레지스트리가 `http/https`만 통과시켰다. 셸 파드의 주소는 `ssh://user@host`
   이므로, "무엇이 올바른 주소인가"를 드라이버(`normalize_url`)로 내렸다.
2. **워크플로우 필수 가정** — 업로드가 항상 `.json` 워크플로우를 요구했다. 템플릿에
   `requires_workflow: false`를 두어 워크플로우 없는 작업을 허용했다.
3. **템플릿↔파드 종류 매칭** — 안 막으면 ComfyUI 파드에 셸 작업이 들어가 조용히 엉뚱하게 돈다.
   템플릿에 `pod_kinds`를 두고 서버와 화면 양쪽에서 걸렀다.

이 셋은 다음 워커(글 쓰기, 지도 그리기)를 붙일 때 **다시 나오지 않는다** — 이미 일반화됐다.

**이미지가 아닌 산출물**: 셸 파드가 남기는 `shell_<n>.txt`는 결과 이미지와 같은 `job_id` 폴더에
쌓이는데, 갤러리는 **깨지지 않고 그냥 무시한다**(확장자로 이미지만 훑으므로). 카드 썸네일에도
안 잡히고 에러도 없다. 즉 "안전하지만 보이지 않음". 화면에서 다루려면 갤러리를 "산출물 +
타입별 뷰어"로 일반화해야 하고, 그건 그런 워커가 실제로 필요해질 때 한다.

**부수 소득**: 옵션에 `required`를 넣어 "비면 애초에 성공할 수 없는 작업"을 큐에 넣기 전에
막게 했다(셸 명령이 비어 있는 경우). 모든 템플릿이 쓸 수 있는 일반 기능이다.

### P4 — 화면을 파드 스코프로 재편

P0~P3으로 **데이터**는 파드별이 됐는데 **화면**은 그대로였다. 상단에 작업·Danbooru·워크플로우·
모델 탭이 전역으로 놓여 있고, 그 셋(작업 제외)은 늘 기본 파드만 봤다. 파드가 여럿이면 화면이
어느 파드 이야기를 하는지 말해주지 못하는 상태 — 그걸 정리한 단계다.

- [x] 전역 탭을 대시보드·갤러리·Danbooru로 줄이고, 작업·워크플로우·모델을 파드 안으로
- [x] 파드 스코프 바 (돌아가기 · 상태 점 · 파드 전환 · 종류 · 설정 · 서브탭)
- [x] `#pod/{id}/{sub}` 라우팅, 옛 링크(`#jobs`/`#builder`/`#lora`) 자동 이관
- [x] 파드 종류가 서브탭 구성을 정함 (`POD_SUBTABS`) — 셸 파드에는 작업 탭만
- [x] 화면 사이 넘김 4곳을 파드 인지하도록 수정
- [x] `object_info`를 파드별로 — `?pod_id=`로 그 파드에 물어봄
- [x] 대시보드에 "최근 작업" 카드 — 작업 목록이 파드 안으로 들어가며 비는 자리를 대신
- [x] 검증: 파드 3개(ComfyUI 온라인·ComfyUI 오프라인·셸)로 라우팅/넘김/등록/큐 제어

**왜 Danbooru만 전역에 남겼나.** 넷 다 "이미지 생성 도메인"에 속하지만, 파드에 종속되는 것과
도메인에 종속되는 것은 다르다. 워크플로우·모델은 그 파드의 `/object_info`를 읽고, 작업 목록은
그 파드의 큐를 읽는다. Danbooru는 태그 풀과 히스토리를 nightshift 로컬 JSON에서 읽을 뿐
파드를 쓰지 않는다 — 파드 안에 넣으면 "파드 A의 태그 풀"이 따로 있는 것처럼 보이는데 실제로는
하나뿐이라 거짓말이 된다.

**이 재편이 실제로 고친 것** (전부 원래 있던 결함인데, 화면이 전역이라 가려져 있었다):

1. **셸 파드만 등록해도 🧩·🎛 탭이 그대로 보였다.** `pod_kinds`로 템플릿↔파드는 걸러지는데
   탭은 HTML에 정적으로 박혀 있어 필터가 안 걸렸다. 이제 파드 종류가 서브탭을 정한다.
2. **워크플로우·모델 화면이 늘 기본 파드를 봤다.** 파드 B 안에서 파드 A의 노드 목록을 보고
   "✅ 이 서버에서 돌아갑니다"라고 답하던 자리다. `object_info_pod(pod_id)`로 정리했고,
   화면 캐시도 파드별로 무효화한다.
3. **파드 하나만 켜면 다른 파드의 대기 작업까지 끌어왔다**(`start_pods`). "파드 하나만 켠다 =
   다른 파드는 안 쓴다"는 옛 가정인데, 작업 화면의 ▶ 시작이 늘 파드 하나만 켜게 되면서
   파드 A에서 시작을 눌렀을 뿐인데 파드 B의 작업이 A로 끌려왔다. 이제 **배정된 파드가
   사라졌거나 꺼진** 작업만, 그것도 **워커 종류가 맞을 때만** 되돌린다.
4. **"🗑 완료 삭제"가 전역이었다.** 파드 하나를 보고 있는 화면의 버튼이 안 보이는 파드의
   작업까지 지웠다. `?pod_id=`로 좁혔다.

**"실행할 파드" 드롭다운을 없앴다.** 파드는 이제 주소가 정한다(`#pod/{id}/jobs`). 대신 파드
스코프 바의 파드 전환이 그 자리를 대신하는데, **전환해도 새 작업 폼은 그대로 남는다** — 그래야
"프롬프트를 다 채운 뒤에 어디서 돌릴지 정하는" 순서가 살아 있다. 파드 *종류*가 바뀔 때만
템플릿 목록을 다시 그린다(그때는 쓸 수 있는 템플릿 자체가 달라지므로).

**비용**: 대시보드 → 파드 → 작업으로 클릭이 한 번 늘었다. 파드가 하나뿐인 지금은 순수 손해고,
파드가 여럿일 미래를 위해 현재를 조금 지불하는 거래다.

## 6. 원칙

1. **각 단계 끝에서 항상 동작한다.** P0이 끝나면 화면이 그대로여도 내부는 파드 모델이다.
   중간 상태에서 기능이 깨진 채로 다음 단계로 넘어가지 않는다.
2. **기존 설정은 자동 이관한다.** 사용자가 손으로 옮겨 적을 일이 없어야 한다.
3. **드라이버 seam은 지금, 드라이버 구현은 필요할 때.** 자리는 만들되 없는 워커를 위한
   구현은 안 한다(P3의 `shell`은 예외 — 이질성 자체를 검증하는 게 목적).
4. **관례 유지**: `templates/*.py`는 서로 import하지 않고 복사로 공유, 설정은 코드에 기본값 +
   `.env` 오버라이드, 저장소는 통째로 덮어쓰는 JSON.

## 7. 지금 하지 않을 것

- **갤러리의 산출물(artifact) 일반화** — 이미지 아닌 결과물을 내는 워커가 실제로 생길 때.
  `output_images.py`는 확장자로 이미지만 훑고 썸네일·회전·zip·이메일이 전부 이미지 전제라,
  손대면 범위가 크게 번진다.
- **RunPod API 연동(파드 자동 생성/종료)** — 수동 주소 등록으로 충분한지 먼저 확인한다.
- **파드 간 모델 자동 동기화** — 네트워크 볼륨으로 풀릴 가능성이 높다.
- **자동 작업 배분 정책** — 독립 큐 + 수동 이동으로 먼저 써보고 필요가 확인되면 추가.
